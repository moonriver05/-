# 维基百科数学与算法语料本地化可行性核算

核算日期：2026-09-15。结论面向中文维基百科首期 MVP，英文语料另列为扩展方案。

## 结论

只保存中文维基百科数学与算法相关的当前正文、章节、公式、来源和必要元数据，不保存全量图片与完整修订历史时，普通个人电脑足以存储和开发。

建议第一期控制在 **8,000–20,000 篇核心条目**，全套在线数据（MySQL + Elasticsearch + RAG 分块及向量 + 社区数据）预计 **6–15 GB**。导入期间连同压缩包、临时空间和 Docker 镜像，建议预留 **至少 35–60 GB**。16 GB 内存可以开发，MySQL 与 Elasticsearch 同机运行时 24/32 GB 更舒适。

当前开发机 C 盘实测仅剩约 **44.1 GB**：可以完成核心库，但应采用流式解析、导入完成后删除中间文件，或把下载文件和 Elasticsearch 数据目录放到另一块 SSD。

## 可验证的上限

- 2026-09 中文维基 `pages-articles.xml.bz2`（当前正文，不含完整历史）压缩文件约 **3.40 GB**；multistream 版本约 **3.58 GB**。
- 同期英文维基相同类型文件约 **25.68 GB**，multistream 约 **26.80 GB**。英文全量不适合当前只有 44 GB 空闲空间的开发盘。
- Wikimedia 在 Hugging Face 上发布的 2023-11 中文清洗正文 Parquet 全库约 **1.72 GB**。它说明即使把中文全站清洗正文存下来，正文数据本身仍处于个人电脑可承受范围；当前版本会更大，但数量级没有发生根本变化。
- 一项 2024 年数据集论文从英文数学专用无图片 dump 中提取了 **106,881 篇、约 8 亿 token**。中文数学内容显著少于英文，可据此把广义中文数学/算法集合看作“数万篇”，而不是“百万篇”。

## 为什么不能直接报一个唯一的“数学条目数”

维基分类是带环的图，不是严格的学科树。“数学”根分类的直接正文很少，大部分内容位于多层子分类；向下遍历过深又会混入数学家传记、历史、教育、软件、物理、金融等相邻主题。因此条目数量主要取决于项目对“相关”的定义。

建议将范围写进大创项目立项材料：

| 范围 | 收录规则 | 预计条目 | 适合阶段 |
|---|---|---:|---|
| 教学核心库 | 人工白名单学科 + 常见算法清单 | 2,000–8,000 | 原型、答辩演示 |
| 推荐首期 | 白名单分类向下 3–4 层 + 去重 + 主题分类器 | 8,000–20,000 | 大创一期 |
| 广义领域库 | 数学/算法及交叉学科，包含人物、软件、应用 | 20,000–50,000+ | 后续扩展 |

精确数值应由一次“只抓 ID 和长度、不抓正文”的盘点任务得到。盘点输出 `page_id/title/categories/revision_id/byte_length`，通常仅几十 MB，得到真实均值后再决定正式下载。

## 推荐首期容量模型

以 20,000 篇正文、平均清洗后 25 KB、平均每篇 8 个 RAG 分块、768 维 float32 向量为例：

| 数据层 | 估算方式 | 预计空间 |
|---|---|---:|
| MySQL 正文与元数据 | 约 0.5 GB 原文 + 行/索引/版本余量 | 1–2 GB |
| Elasticsearch 全文索引 | 正文副本、中文分词、倒排索引 | 1–3 GB |
| RAG 分块文本 | 160,000 段及来源定位 | 0.7–1.5 GB |
| 768 维向量 | `160000 × 768 × 4` 约 0.49 GB 原始值，加 ANN 图和元数据 | 0.8–1.8 GB |
| 社区批注、讨论、AI 记录 | 早期用户量，设增长余量 | 0.5–2 GB |
| 数据库日志、备份与余量 | binlog、段合并、临时文件 | 2–5 GB |
| **合计在线数据** | 不含原始 dump 和 Docker 镜像 | **6–15 GB** |

上述数值是工程容量规划，不是最终实测值。导入前应先随机抽取 500–1,000 篇，测量平均 WikiText、清洗正文、章节数和分块数，然后用 P95 而非只用平均值进行二次核算。

## 不建议“逐页爬 HTML”

批量初始导入应使用 Wikimedia 官方 dump，不要用爬虫逐页请求网页：

1. 下载 `page.sql.gz`、`linktarget.sql.gz`、`categorylinks.sql.gz` 和 `pages-articles-multistream.xml.bz2`。
2. 用 page/linktarget/categorylinks 在本地建立分类图，以白名单、最大深度和黑名单筛选 page_id。
3. 流式读取 bzip2 XML，遇到目标 page_id 才解析并入库；不要先完整解压到磁盘。
4. 保留 `page_id`、`revision_id`、原页面 URL、许可和更新时间，正文按章节拆分。
5. 后续仅用 RecentChanges/EventStreams 或 API 做增量同步，并实现指数退避。

官方 API 使用规范要求明确 User-Agent、遵守限速与机器人规则；大规模内容复用更适合 dump。参考：

- https://foundation.wikimedia.org/wiki/Policy:Wikimedia_Foundation_API_Usage_Guidelines
- https://foundation.wikimedia.org/wiki/Policy:Wikimedia_Foundation_User-Agent_Policy

## 图片、公式和历史版本

- **图片**：首期不要全量本地化。只保存 Commons 文件页、缩略图 URL、作者与许可元数据，访问时按需缓存经过审核的少量图片。图片体量及许可差异会远大于正文。
- **公式**：保留 WikiText 中的 TeX 源码，在前端用 KaTeX/MathJax 渲染，不需要把公式转成图片存储。
- **历史版本**：首期只保存当前 revision_id 和本项目自身的版本历史。完整维基修订历史会把容量扩大一个数量级以上，且并不是 RAG 必需数据。
- **讨论页**：不批量搬运原维基讨论页；平台社区内容使用自己的表和审核流程。

## 许可必须进入产品设计

维基文本复用需要遵守 CC BY-SA：每篇条目展示原页面链接/归属、许可、抓取 revision_id 和修改说明；基于原文修改后的可版权内容需要采用相同方式共享。媒体文件逐个遵守其文件页许可，不应默认认为都与正文相同。

参考：https://foundation.wikimedia.org/wiki/Legal:Wikimedia_Developer_App_Guidelines

## 立项建议

项目应采用“中文教学核心库 → 广义中文领域库 → 可选英文补充”的三级路线。首个里程碑先盘点 8,000–20,000 篇候选条目并完成 1,000 篇端到端导入；只有在检索准确率、公式解析率和许可证展示达标后再扩大范围。这样既能在个人电脑完成，也能避免为了追求数量导入大量与学习目标无关的页面。

## 本项目实测结果（2026-09-15）

本地解析 2026-09 中文维基官方 dump 后得到：

- 页面或分类页面元数据：3,641,269 条。
- 分类目标：1,201,874 条。
- 分类关系：23,366,040 条。
- 26 个数学/算法教学根分类，向下遍历不超过 3 层，共访问 1,465 个子分类。
- 去重后的宽松候选：32,664 篇。
- 进入正文解析的高优先候选：8,000 篇，全部从 dump 中找到。
- 通过正文教学特征过滤：5,420 篇。
- 最终核心教学库：按教学得分保留 5,000 篇。
- 最终简体纯正文：26,166,254 字节；包含原始 WikiText、章节、分类、来源和许可的数据文件约 104 MB。
- E 盘当前语料、元数据索引及中间文件合计约 5.7 GB。

该结果证明个人本地存储完全可行。32,664 是宽松分类候选而不是建议发布量；项目一期使用经过二次过滤的 5,000 篇核心条目。
